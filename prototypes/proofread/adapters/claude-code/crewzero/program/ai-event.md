# 你今次嘅工作：整理一件真實事件嘅影響

創辦人記錄咗一件公司以外真係發生咗嘅事（例如見咗伙伴、對方答應咗乜、收到回覆）。你要判斷呢件事改變咗邊條假設嘅證據級、令邊個站完成，交建議；**你唔可以自己改**，外殼會按你嘅建議出確認問題，創辦人逐項確認先生效。資料喺同一個資料夾：

- `event.md`：創辦人原話同事件日期；`files/`（如有）係創辦人交嘅證明文件。
- `ledger.json`：公司紀錄而家嘅站（`milestones`：名稱、真事、見證、證明、完成標準、`done` 係咪已完成）、假設清單（`assumptions`：內容、而家嘅級別 `grade`）、而家嘅下一個對外動作（`nextExternalAction`）、人物及機構名單（`actors`）同常用名稱表（`terms`）。
- `confirmed-page.md`：創辦人確認咗嘅公司概覽。
- `context.md`（如有）：外殼按今次參加者選出嘅已確認以往紀錄；只供對照。

## 讀附件嘅方法

- `event.md` 已逐份列出附件檔名（喺 `files/`），直接按檔名讀，唔使列資料夾。
- PDF：收件時已由 CrewZero 轉成文字版（同名 `.md`，`event.md` 會寫明），讀文字版即可。冇文字版（例如掃描圖片型）先用讀檔工具**一次過讀整份**，唔好用 `pages` 參數分頁讀（分頁讀要電腦另外裝軟件，會報錯）；仍然讀失敗就列入 `unreadable`（見下）。
- Word、PowerPoint、Excel 檔（.docx、.pptx、.xlsx）收件時已由 CrewZero 轉成文字版：`event.md` 會喺該附件下一行寫明「文字版：files/<檔名>.md（圖片及版面不包括）」，同名 `.md` 就係文字版，讀文字版即可；圖片、圖表同版面唔喺文字版入面，唔好扮睇過。文字版冇出到嘅附件（舊格式、有密碼、太大、損壞、冇內容）先當讀唔到。
- 附件如果來自 Google 連結，`event.md` 會寫明原連結同讀取日期；你讀嘅係嗰日嘅快照，唔好喺 `out/` 寫「已開啟連結」。
- 每個讀唔到嘅附件都寫入 `out/event.json` 嘅 `unreadable` 清單：`file` 只寫檔名本身（例如 `會後紀錄.docx`），唔好加 `files/` 或其他路徑；`reason` 用書面語寫一句原因（最多 80 字，超過會被截斷；只供紀錄，唔會直接顯示畀創辦人，亦唔好寫工具名稱或參數名）；外殼會逐份用固定字句告訴創辦人哪些檔案未能讀取，並按檔案類型給建議（Word、PowerPoint、Excel：請另存為 PDF 再交，或在「告訴 Zero」頁直接寫下文件重點；PDF：請分拆為每份 100 頁以內、移除密碼後再交，或直接寫下文件重點；其他格式：請改交 PDF，或直接寫下文件重點）；你只需要列出檔名，唔使喺任何欄位寫建議。`summary` 只寫事件重點（最多 300 字），唔好喺 `summary` 列檔名。

## 證據級（只計對方嘅行為）

- `guess` 假設：只係假設，未有人表示或行動。
- `said` 口頭表示：對方表示有需要或有興趣。
- `did` 實際行動：對方已經做咗一件事，例如安排咗會面、交咗資料、真係轉介咗某一個人。
- `paid` 付出成本：對方付出金錢、時間或承諾，例如落單、簽約、出資。
- `stuck` 形成依賴：對方已經依賴，停用會有損失。

判讀：只計對方**已經做咗**嘅事；對方「答應」「表示願意」「會考慮」但未做，只算 `said` 口頭表示。同一個人講多幾次唔升級；可用性（對方用過）唔等於會付錢；伙伴願意引薦只係渠道訊號，唔證明對方會負責銷售或者付錢；創辦人自己做嘅事、AI 做嘅研究都唔係證據。對方取消、否認、拒絕就建議降級。拿唔準就揀低一級。

## 會議紀錄附件（如有）

如果 `event.md` 指出有 `files/會議紀錄.md`，它是這次判讀的主要來源。

- `⚠️（原因）` 的內容尚未核對：可以提出確認題，但不得當作已確定事實。
- `✏️（要補甚麼）` 代表該欄未知；不得自行補上日期、負責人、姓名或對方資料。日期未知時不要提出日程題。
- 相對日期（例如「下星期」）只有在 `event.md` 有會議日期時才可換算成 `YYYY-MM-DD`；`why` 必須寫明「由『下星期』換算」，並把它當作需要確認的內容。沒有會議日期時寫「日期待定」，不要列 `followUp`。
- `event.md` 列出「創辦人今次改動了以下各行」時，這是創辦人修改後的版本：改動行以修改後內容為準，即使與逐字稿或紀錄其他段落不一致；涉及已改動的待辦、日期或下一個對外動作，按修改後內容列出，`sourceQuote` 引用修改後的行，不一致之處在 `why` 提醒創辦人核對。
- 每一項另加 `sourceQuote`：從會議紀錄逐字抄一段足以唯一找回來源行的短引句。外殼會按它找出實際來源行，再核對該行有沒有 `⚠️` 或 `✏️`；找不到或找到多行都會退回你核對。`why` 仍然寫給創辦人看的理由，毋須照抄引句。
- 不得在 `summary`、`why`、`text`、`action`、名稱或其他輸出欄位留下 `Speaker N`、`Unknown Speaker` 等未確認講者標籤；未能對照實際姓名就不要提出該項。

## 以往紀錄（context.md，如有）

如果有 `context.md`，今次嘅 `files/會議紀錄.md` 仍然係唯一可用嚟判讀今次會上發生咩事嘅來源。

- 假設級別同站係咪完成，只可以按今次會議紀錄判斷；唔好因為以往紀錄而升級、降級或者判完成。
- 唔可以把 `context.md` 內容寫入 `summary`、`read`、`action` 或 `text`；只可以用嚟作下面兩類對照。
- `followUp` 如果同 `context.md` 一項日程係同一件事（同一對象、同一行動，只係日期或細節改變），加 `sameAsTask`，值係嗰項日程編號；唔肯定就唔好填，當新跟進。
- 頂層 `contrasts` 係清單，冇對照亦要寫 `[]`。每項係 `{ "nowQuote": "今次會議紀錄逐字引句", "pastQuotes": ["以往逐字引句，最多三句"], "note": "一句白話說明" }`。
- `contrasts` 只可以用喺前後說法矛盾，或者數字、日期、條件改變；對方提出新要求、話題唔同都唔算。今次引句一定要逐字出自今次會議紀錄；每句以往引句一定要逐字出自 `context.md` 或公司概覽嘅「邊個要點頭」一行。
- 今次講「上次」「之前」而有多個可能時，`pastQuotes` 必須列出全部候選（最多三句），`note` 寫明未能確定；唔可以只揀一個。
- 對方答應某事、但公司概覽該站寫嘅決策者唔在今次參加者之內，可以列對照。所有對照只指出差異，唔判斷邊個啱，唔提出任何改動；`note` 唔可以寫「已更新」或「將會加入」。

## 要做

寫 `out/event.json`：

```json
{
  "summary": "一句講呢件事：邊日、同邊個機構邊個人、對方講咗或者做咗乜",
  "unreadable": [{ "file": "會後紀錄.docx", "reason": "Word 檔案目前無法讀取" }],
  "grade": "did",
  "read": {
    "summary": "一兩句：我讀咗創辦人原話同邊幾份附件，對照咗邊幾條假設、邊幾個站",
    "highlights": [
      { "text": "文件重點一句（日期、金額、責任或跟進，每類各一句，有就寫、冇就唔好湊數）", "page": 3, "file": "會議紀錄.pdf" }
    ]
  },
  "contrasts": [
    { "nowQuote": "今次會議紀錄逐字引句", "pastQuotes": ["以往逐字引句"], "note": "一句白話說明" }
  ],
  "reason": "只喺 items 係空清單時必填：一句講清楚點解呢件事冇改變任何假設、站或下一個對外動作",
  "items": [
    { "kind": "assumption", "id": "H2", "grade": "did", "sourceQuote": "對方已安排下次會面", "why": "一句理由：對方做咗乜，所以去到呢一級" },
    { "kind": "milestone", "id": "m1", "done": true, "sourceQuote": "雙方已簽署試用確認", "why": "一句理由：邊樣紀錄符合呢個站嘅完成標準" },
    { "kind": "nextAction", "text": "下一個對外動作（一句：對誰、做乜、幾時）", "milestoneId": "m2", "sourceQuote": "下星期先寄出試用樣本", "why": "一句理由" },
    { "kind": "newActor", "name": "黃小姐", "org": "乙餐廳", "role": "負責人", "actorKind": "customer", "sourceQuote": "乙餐廳黃小姐負責安排試用", "why": "一句理由：原話提到她是誰、為甚麼值得記入名單" },
    { "kind": "newTerm", "name": "星塵慢烘禮盒", "termKind": "product", "sourceQuote": "星塵慢烘禮盒下星期推出", "why": "一句理由：這是公司新推出產品的專有名稱" },
    { "kind": "followUp", "date": "2026-11-20", "action": "一句要做乜（例如：回覆甲公司報價）", "station": "m2", "sameAsTask": "fu-in-20261103-q2（只有同一件既有日程先寫）", "sourceQuote": "11 月 20 日前回覆", "why": "一句理由：文件或原話哪裏寫明呢個日期" }
  ]
}
```

0. `unreadable`：只列讀唔到嘅附件，`file` 只寫檔名（唔加 `files/`），一定要係今次附件嘅檔名；全部讀得到就省略或者寫 `[]`。未能讀取嘅附件唔可以當作「冇資料」去推斷。
1. `grade`：呢件事本身去到邊一級（對方做咗乜）。
2. `items` 每項只講一件事，最重要排先；外殼每包最多問三題，第四項起會留待下一包，不可因為題數而省略：
   - `assumption`：`id` 用 `ledger.json` 入面嘅假設；`grade` 係你建議嘅新級別，同而家一樣就唔好列。
   - `milestone`：`id` 用 `ledger.json` 入面未完成嘅站；只可以建議 `done: true`。只有事件符合嗰個站嘅真事同完成標準、而且有紀錄（會議紀錄、對方書面回覆、收據、證明文件）先建議完成；只係進展、未完成就唔好列。
   - `nextAction`：呢件事做完咗而家嘅下一個對外動作（例如會面已經見咗），或者事件定咗新嘅下一步（例如約咗下次見面），就建議新嘅下一個對外動作；`milestoneId` 係佢屬邊個站（可以省略）。同而家一樣就唔好列。
   - 唔改變任何假設、站或者下一個對外動作，就寫 `"items": []`，喺 `summary` 講清楚。
   - `followUp`：文件或創辦人原話**明確寫出**嘅跟進日期（例如「11 月 20 日前回覆」）；`date` 係真實日期（YYYY-MM-DD），不可早過事件日期；`action` 一句要做乜（最多 80 字）；`station` 可省略，有就要係 `ledger.json` 入面嘅站；日期要有明文依據，唔好自己估。`sameAsTask` 只喺「以往紀錄」規則確實屬同一件既有日程時寫。創辦人確認「加入日程」之後先會變成佢嘅一項行動。
   - `newActor`：原話或附件文字版**第一次**提到、而 `ledger.json` 的 `actors`（公司以外的人物及機構名單）內未有嘅人或機構。`name` 必須**逐字**出現在創辦人原話或附件文字版（只在圖片內見到嘅名字不接受；PDF 文字版內嘅名字可以用；亦唔好用代稱或簡稱）；`org`、`role` 各最多 40 字，可省略；`actorKind` 係 `customer`（客戶）、`partner`（供應或合作方）、`investor`（投資者或資助方）、`advisor`（顧問或協助者）、`team`（團隊成員）之一，揀 `team` 時要加 `teamType`（`cofounder`、`fulltime`、`parttime`、`contractor`）同 `role`。**只可以寫名稱、機構同角色：唔好寫電話、電郵、地址、社交帳號、薪酬、合約或任何人事資料**（寫咗會被退回）。每件事最多一項；名單內已有（或曾用名）嘅唔好再列；創辦人確認「加入名單」之後先會記入。
   - `newTerm`：只限公司自己的產品、服務、活動、計劃或其他專有名稱；人、公司、機構一律用 `newActor`。`name` 必須逐字出現在創辦人原話或附件文字版；有會議紀錄時只可用 `files/會議紀錄.md` 內的寫法，`sourceQuote` 所在行亦必須包含這個名稱；帶 ⚠️ 或 ✏️ 的行，以及「改動清單」內的寫法，都不要提出新名稱。`termKind` 只可用 `product`（產品或服務）、`campaign`（活動或計劃）或 `other`（其他專有名稱）。`ledger.json` 的 `terms` 及 `actors` 已有的名稱或另一個寫法不要再列；普通字詞、工作範疇、片語不要列。每件事最多一項；創辦人確認加入後才會記入常用名稱表。
3. `read`：`summary` 係一兩句（最多 200 字），講你讀咗乜、對照咗乜；`highlights` 係「文件重點」，最多八項，日期、金額、責任、跟進各一句（每句最多 120 字），讀自 PDF 時 `page` 寫頁碼數字（可省略），`file` 寫該附件檔名（可省略）；只寫文件或原話明文寫明嘅內容，唔好推斷。冇附件都要有 `read`，`highlights` 可以係空清單。`read` 同 `reason` 都係創辦人睇到嘅字：用日常白話書面語，唔好寫 `H2`、`m1` 呢類編號。
4. `reason`：`items` 係空清單（冇任何確認題）時必須填寫，一句（最多 120 字）；有確認題時可以省略。
5. 有會議紀錄附件時，每一項都必須有 `sourceQuote`（最多 160 字）：逐字抄自同一份紀錄、足以唯一定位一行；不可只靠概括字眼、不可編造或跨行拼湊。`why` 一句，寫俾創辦人睇：講對方做咗乜、點解係呢一級；唔好寫 `H2`、`m1` 呢類編號、級別英文字或者數字級。
6. 唔好估紀錄冇寫嘅事；唔清楚就唔好列，喺 `summary` 寫明仲未知乜。

## 規矩

1. 只可以讀寫呢個資料夾；所有產出只寫入 `out/`。
2. 唔好寫問題包（`out/ask.json`），確認問題由外殼出。
3. 用日常白話；唔好用內部工程術語、檔案路徑；唔好 AI 腔。
